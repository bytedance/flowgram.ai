# 复杂项目实证验证 · 2026-10-19

结论：三个业务工程已在实际桌面服务中运行，15 项业务断言通过；发现的执行、契约与展示问题已修复。这里证明的是所列编排与故障语义，不等于已经接入生产 ERP、支付或 CRM。

## 可直接打开的工程

| 工程 | 实际内容 |
|---|---|
| 复杂验证 · 订单履约 | 去重 → 并发逐单 → 并行查客户/库存 → 风险/库存分流 → 原子预留 → 履约/人工/缺货台账 → 汇总 |
| 复杂验证 · 采购对账 | 并行取发票/采购单/收货单 → 两次关联 → 三单匹配 → 缺单/数量/金额/币种分流 → 幂等台账 |
| 复杂验证 · AI 客服 | 并行上下文 → 真实模型 → JSON 与 Schema 校验 → 敏感操作硬约束 → 回复草稿/紧急/人工分流 → 重放复用决定 |

10 条可复用业务工作流共 152 个节点定义；另有内置 Agent 创建的 9 节点异常日报与两条依赖版本验证探针。主流程、可复用单项流程和 HTTP 重试流程分别保存，没有把业务规则移进外部服务伪装成编排。

业务服务使用受控的非生产样本；HTTP、SQLite 库存/台账、模型调用和 Rust 执行都是真实的。金额样本使用最小币种单位；日报按币种分组，不把不同币种累加或统一标成人民币。

## 遇到并闭环的问题

| 问题 | 复现与修复 |
|---|---|
| 基础节点不能查询完整契约 | http / llm / subworkflow 查询实际失败；补齐全部基础节点的英文契约，与扩展节点共用发现入口 |
| 大图工具参数过小 | Agent 原先仅接受 20KB；改为有界 512KB，并回归超过 20KB 的百节点参数及越界输入 |
| 运行期间读到新子流程版本 | 旧实现实测应为 version=1 却得到 2；现在运行前冻结传递依赖，旧运行保持 1，后续 MCP 运行得到 2；单节点测试一致 |
| 子流程节点 ID 污染主图状态 | 事件增加 workflowId，按流程过滤；节点终态独立聚合，过程按页读取 |
| 客服重放重新生成模型内容 | 旧流程 4 个重复请求都发生幂等冲突；增加已提交决定查询，重放不再执行模型也不重复写入 |
| Agent 生成日报只校验结构便报完成 | 真实执行暴露模板取错聚合字段；补全 row.key 输出契约，把错误反馈到真实 Agent，会话内修复原流程、单节点测试并整流程成功 |
| 非法重复节点 ID 导致校验器溢出 | 新回归真实触发 panic；拓扑排程提前拒绝重复 ID，校验正常返回诊断 |
| 运行输入不适配真实工程 | 移除固定示例消息，使用 Schema default；整数保留类型，打开试运行保留草稿，后端在副作用前验证输入契约 |
| 控制流诊断仍含中文 | 改为英文契约与诊断，界面通过翻译目录呈现中文 |

Agent 构建会话保留在采购工程“Agent 构建验收 · 采购异常日报”。第一次构建中它从结构错误恢复；实际运行又发现模板错误，由验收方回传真实错误后，它修改原工作流并完成 test_node 与整流程运行。未将这两轮描述成一次无干预成功。

- Rust：64 项测试、fmt 检查、Clippy（warnings 视为错误）通过。

最后一处“重新打开试运行保留输入”的修复已通过前端检查并进入新桌面构建。收尾时 Mac 已锁屏，为保留当前窗口与草稿未再次重启原生应用；该修复在下次启动后生效。上述 15 项业务运行已在当前 Rust 服务完成。

执行命令、故障注入与运行边界见 [验收脚本说明](../server/validation/README.md)。业务服务持续运行在独立的 `flowgram-business-validation` tmux 会话中。

## 尚未证明或未实现的边界

- 人工分流目前写入审核台账，不是跨进程持久化等待审批的引擎。
- 不具备跨进程断点续跑、通用补偿事务或对任意外部系统的 exactly-once 保证；幂等由具体业务资源与工作流协同实现。
- 已冻结工作流依赖，尚未统一冻结模型连接、外部资源与凭证绑定。
- 金额节点仍有浮点运算边界；本次证明整数最小币种单位样本正确，未证明任意精度账务能力。
- 万条事件通过分页读取，但未声称事件列表已具备超大规模虚拟化能力。
