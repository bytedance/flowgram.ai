# FlowGram 对话与轮次信息架构

状态：分阶段实现。首阶段已完成 Rust 持久化 Turn / Item / 输入协议、工具生命周期、队列与本轮补充、停止确认和刷新恢复；询问、审批、检查点与语义化工具聚合仍是后续设计。下文保留完整目标，不能将未实现部分视为当前能力。

对话围绕用户的一次请求组织为一轮工作。每轮保留用户输入、执行过程、需要用户处理的事项，以及可打开的工作流和运行结果。进行中突出当前动作，结束后突出结论与成果；详细过程始终可回看。对话轮次、工具调用和工作流运行分别记录状态，通过明确引用关联。

工程归属、目录、会话与工作流关系以 [项目工程与 App 信息架构](agent-workflow-app-information-architecture.md) 为准。本文统一使用“会话”；Session 命名、显式工程范围和项目目录内存储已完成替换；不保留旧 Task 接口。轮次交互继续遵循 [桌面设计规范](desktop-design-system.md)。用户不需要学习 Thread、Item、Tool Call 等内部名词；界面使用“本轮”“处理过程”“待办”“运行记录”。

## 现状与改造目标

改造前，对话将 `messages` 和 `tool_finished` 按时间戳排序，正文与工具结果没有共同的轮次身份。流式文本暂存在按会话区分的字符串中；工具开始事件没有对应的常驻展示，工具结果基本只有名称和成功标记。发送按钮在运行中不可用，失败主要表现为全局错误和一条助手文本。

因此需要先改变信息组织，再调整组件：

| 当前问题 | 下一版的要求 |
| --- | --- |
| 多条助手消息看不出属于哪次请求 | 同一轮具有稳定边界；一轮可以含多段正文和多次工具调用 |
| 工具完成后才出现，看不到正在做什么 | 开始、等待、执行、返回、失败在同一行原地更新 |
| 过程占满历史，正文与结果分散 | 历史默认显示用户输入、过程入口、最终回复和成果 |
| 工具返回成功被误读为业务执行成功 | “已发起运行”与“运行已完成”分别展示 |
| 运行中无法继续沟通 | 输入框保留；发送后进入消息队列，队列可显式调整当前任务方向 |
| 刷新可能丢失流式内容与过程关联 | 运行态与历史使用同一份后端读取模型 |
| 无从判断停止、重试会影响什么 | 停止范围、保留成果、重试边界和外部操作结果明确 |

## 成熟方案的取舍

以下是公开资料能够确认的行为，以及 FlowGram 的设计选择，不声称复刻其他产品的完整实现。

| 参考 | 可确认的行为 | FlowGram 的选择 |
| --- | --- | --- |
| [Codex Queue 与 Steer](https://developers.openai.com/blog/mastering-codex-remote-for-engineering) | 区分等待下一轮与调整进行中的工作 | 发送默认排队；已排队的消息可通过“调整方向”投递给当前任务 |
| [Codex App Server](https://learn.chatgpt.com/docs/app-server) | Turn 与 Item 各有生命周期；工具结束、轮次结束和审批响应是不同事件 | 后端提供独立对象与权威状态，前端不按文本、时间或请求 ACK 猜测完成 |
| [Claude Code 交互模式](https://code.claude.com/docs/en/interactive-mode) | 工具细节可展开，连续调用可压缩；运行中输入有明确的接收行为 | 默认紧凑过程摘要，展开单次工具；不照搬终端快捷键与终端密度 |
| [Claude Artifacts](https://support.claude.com/en/articles/17153992-what-are-artifacts-and-how-do-i-use-them) | 可编辑成果与对话并置，便于继续处理 | 工作流与运行在工作区打开，对话保存引用和本轮成果摘要 |
| [Cursor Checkpoints](https://docs.cursor.com/en/agent/chat/checkpoints) 与 [Claude Code Checkpointing](https://code.claude.com/docs/en/checkpointing) | 修改恢复有范围，不能视为所有操作的通用撤销 | 工作流恢复创建新版本；聊天重试不承诺撤回 HTTP、MCP 或其他外部操作 |

## 对象与归属

```text
项目
├── 会话
│   ├── 一轮工作
│   │   ├── 用户请求与当时的工作流、节点、运行引用
│   │   ├── 本轮补充输入
│   │   ├── 有序内容：助手说明、工具调用、询问、确认、结果引用
│   │   ├── 最终回复（可为空，不能用最后一段过程文字冒充）
│   │   └── 本轮结果：完成、失败或已停止；耗时与成果引用
│   └── 待办输入：尚未被接收执行的后续请求
├── 工作流资源包
│   ├── 当前工作副本与公共输入输出接口
│   └── 完整依赖发布包
└── 运行
    ├── 固定执行定义与资源快照
    ├── 节点执行、流程内 Agent 活动与子运行
    └── 结构化结果与产物引用
```

一轮可以读写多个工作流、发起多次运行；一次工作流运行可能由对话、手动操作或外部 MCP 发起。两者不是一对一关系。会话是持续上下文，一轮是一次明确请求的处理边界，运行是一次工作流执行。

模型请求返回、工具批次结束或模型内部自动续跑都不创建新轮次。用户输入被作为下一轮接收时才创建新轮次；被明确接收为当前轮补充时留在当前轮。后端内部续跑不能伪造成用户消息。

## 工作区的五个区域

以下描述会话独立页或会话与工作流并排时的组织方式，不是整个 App 的默认首页。默认导航以项目内工作流为主；打开画布不自动新建会话，切换画布不改写已提交轮次或排队输入的引用。会话独立页与并排区域复用同一份历史、草稿和队列。

| 区域 | 默认显示 | 操作与定位 |
| --- | --- | --- |
| 当前项目的会话导航 | 会话名称与需要关注的状态 | 区分处理中、待补充、待确认、失败；会话闲置但流程仍在运行时显示运行标记 |
| 会话标题栏 | 名称、当前状态、工作流与运行入口 | 跨轮回看、打开关联成果；不把每个工具做成顶部标签 |
| 对话正文 | 用户请求、过程、介入事项、回复与成果 | 主阅读面；一轮内部保持因果顺序 |
| 输入区 | 草稿、引用与待发送消息 | 始终可输入；等待处理时也保留草稿 |
| 工作区面板 | 画布、本轮变更或运行详情 | 三者共用右侧工作区，不再平行新增一个工具日志常驻面板 |

会话状态是轮次、用户待处理项和关联运行的摘要，不是单个 `running` 布尔值。连线断开单独显示连接提示，不能把进行中的会话改成失败或完成。

## 一轮工作的阅读结构

```text
用户请求                         引用：客户分级 · v12 / 条件节点
  给流程增加高价值客户分支，并用这组数据试运行。

助手说明                         正文，无额外气泡框
  我会先检查现有条件，再调整分支并验证结果。

处理过程                         可展开 / 收起
  读取客户分级                  已完成
  保存草稿 v13                  已保存 · 新增 3 个节点
  校验工作流                    通过
  发起试运行                    已发起 → 运行记录

需要处理的事项                   仅在真实询问 / 策略请求时出现

最终回复                         结论、验证事实、未完成内容
  已增加高价值客户分支，样例数据试运行通过。

成果引用                         客户分级 v13 / 本次运行
结束状态与耗时合并到过程入口，不在最终回复后重复显示
```

### 进行中

显示助手已经发出的进度说明、当前工具或运行、必要的上下文。过程直接显示正文与当前工具组的紧凑摘要，工具组的调用列表和原始详情均按需展开；不把每个 token 或每条底层事件当作一行新消息。

没有可见活动时展示准确的等待状态，例如“正在等待模型响应”“等待工具返回”。不展示模型的隐藏推理，也不把“正在思考”当作贯穿所有阶段的万能状态。进度只使用可证实的计数，不伪造百分比与剩余时间。

本轮补充以独立用户输入显示，并标记接收状态。它处于被接收的位置，不能被并入最初请求、移到轮末或静默消失。排队输入在被接收前只显示在待办区。

### 已完成

默认保留用户请求、过程入口、最终回复与成果引用；用户补充按原顺序保存在可展开的过程内，结束状态合并到过程入口。过程入口放在回复之前，保持“做了什么 → 得到什么”的顺序。

过程折叠是阅读投影，不删除内容。运行中按顺序内联展示正文和工具摘要，不显示整轮“处理过程”开关。完成后使用一个“已处理 · 耗时”的过程入口，最终回复独立保留；纯文本回复没有空的过程开关，也不重复显示完成页脚。完成事件或迟到的最终回复改变默认展开策略，已完成且有最终回复时收起过程；失败、中断默认展开，最新一轮缺少最终回复时也展开，成为旧轮次后正常收起。用户可手动覆盖当前默认值；后台同状态更新不覆盖该选择。

连续工具调用按稳定首 Item ID 合为一个摘要，空白流式占位不拆组；可见正文和本轮补充形成真实分段。工具组默认收起，显示动作与数量、运行状态和失败数量；展开后是调用行，再展开单行才查看参数与原始结果。已纳入本轮的用户补充按原顺序留在过程里。最终回复只按 finalItemId / final phase 识别，不按相同文本去重，不把未完成的说明冒充结果。

消息和 Composer 使用同一 800px 最大容器；输入区两行起步，textarea 48–160px 随内容和宽度自动调整，超出后内部滚动，无手动拉高。模型与本次工作流引用放底栏；不提供本轮 / 下一轮投递方式选择。头部不再重复排列历史关联工作流，输入气泡中的引用显示实际工作流名称。

跟随最新消息只在用户仍跟随底部时发生。上滚、选中文字或手动展开过程 / 工具详情时不跳到底部；点击“回到最新”恢复跟随。加载旧轮次保留阅读位置，切换会话重新建立该会话的尾部定位。

最终回复回答目标是否完成、如何验证、还有什么未完成；工作流名称、版本、结果和动作由成果引用承载。不要让模型把同一组运行 JSON 再完整复制到正文中。

## 工具调用展示

### 三层信息

| 层次 | 内容 | 默认行为 |
| --- | --- | --- |
| 过程组 | 本组意图、当前动作、已完成数量、是否有未解决错误 | 运行中显示当前组；历史默认折叠 |
| 单次调用行 | 动作名称、目标、真实状态、耗时、关键返回信息 | 点击展开该次调用；状态原地更新 |
| 调用详情 | 输入摘要、业务结果、错误与恢复动作；可进一步查看原始参数和返回 | 按需读取；超长内容有截断标记和完整内容入口 |

调用行优先使用“校验 客户分级”“保存 客户分级 · v13”等业务语言。`save_workflow`、调用 ID、原始 JSON 和调试诊断放到详情内，不作为用户的主阅读内容。第三方工具无法识别时显示真实工具名和来源，不编造业务解释。

### 状态与结果

| 状态 | 行内表现 | 展开后的重点 |
| --- | --- | --- |
| 等待执行 | 等待前置步骤 | 依赖和是否已开始 |
| 等待确认 | 需要确认 | 权限策略返回的具体请求 |
| 执行中 | 当前动作；有真实进度时显示进度 | 已有部分输出与耗时 |
| 成功 | 已读取 / 已保存 / 校验通过等具体结果 | 业务字段与成果引用 |
| 已发起异步运行 | 已发起，不写“运行成功” | 关联运行的独立状态 |
| 失败 | 原因摘要，不只显示红色图标 | 已发生的操作、错误范围与允许的恢复动作 |
| 取消中 / 已取消 | 等待停止确认 / 已取消 | 保留部分结果，不伪造回滚 |
| 结果待核实 | 外部结果未知 | 先查询结果；不自动重复有副作用的请求 |

连续、同类、只读的调用可聚合为“读取了 3 个工作流”，展开后保留每次调用。助手正文、用户补充、询问、确认和写操作会切断分组。保存、发起运行等具有独立业务结果的调用不混入“读取了 N 项”。

失败、待确认和结果未知不能被聚合摘要掩盖。自动重试保留每次 attempt；恢复后显示“重试后成功”，不会让早先的失败看起来从未发生。并行调用仍按后端确定的展示顺序排列，先完成的结果原地更新，不按完成时间重排整组。

## 工作流成果与运行结果

### 工作流成果

同一轮对同一工作流的多次编辑，默认形成一个本轮成果摘要，包含工作流名称、起止版本与节点 / 连线变更计数。每次保存仍在过程内可追踪。默认动作是“打开工作流”“查看本轮变更”，普通草稿保存不增加额外确认步骤。

“查看本轮变更”对比本轮基线和本轮结束版本。其他来源插入的修改单独标明，不能把并发手动操作或外部 MCP 修改算给助手。若不具备精确归属，只显示可靠的逐次版本差异；不能展示误导性的累计统计。

历史成果始终引用当时版本；当前工作流已更新时，分别提供“查看当时版本”和“打开当前草稿”。恢复历史版本属于新的写操作，保留后续历史并校验当前版本，不替换过去的消息。

### 运行结果

对话仅显示运行状态、关键输出和“查看运行”；节点树、完整输入输出、流程内 Agent 工具和子流程放到同一运行详情。点击对话引用可定位到运行或失败节点，返回时保留原轮次和阅读位置。

`run_workflow` 返回运行 ID 后，工具调用可以成功结束，工作流仍在运行。助手此时只能说“已发起”。只有运行事件确认后才显示“试运行通过”；若本轮已经结束，运行引用可更新状态，但不静默改写旧的助手回复。

外部 MCP 与手动运行显示真实来源，不凭空生成助手消息。需要排查时，将运行引用加入输入框，由用户发送新请求。

## 运行中的输入与待办

| 用户动作 | 含义 | 反馈 |
| --- | --- | --- |
| 空闲时发送 | 开始新一轮 | 发送中 → 已接收，关联稳定输入 ID |
| 运行中发送 | 当前任务正常结束后处理 | 输入进入待发送消息队列；不伪装成已被助手读取 |
| 编辑 / 移除待办 | 只修改尚未开始的输入 | 后端确认后更新；已派发的输入不显示可撤回承诺 |
| 队列消息“调整方向” | 在当前工具调用结束后将指定输入交给当前任务 | 后端校验活动轮并原子转移；等待接收时显示状态，不得同时保留两份执行 |

输入框只保留一个主动作圆按钮。空闲时发送；任务运行中，草稿为空显示停止，有内容切换为发送并默认提交 `queue`；不要求用户理解轮次或预先选择投递模式。运行中消息出现在输入框上方的队列；“调整方向”只在任务运行且消息尚未投递时可用，悬停说明“在当前工具调用结束后插入”。服务端继续使用显式 `steer` 与目标轮次校验；若任务恰好结束，原消息仍留在队列，展示错误并重新获取权威状态，不能丢失或重复投递。

不支持实时补充的执行器不提供虚假入口。界面说明能力限制，并提供显式的“停止后按新要求继续”；停止确认后创建新轮，不冒充原轮已接收补充。

待办区位于输入框上方，显示顺序、完整输入入口、编辑、移除和投递状态。客户端重载不清空服务端已接收的待办。失败、用户停止或需要核实外部结果时，暂停当前会话的后续待办，显示“继续待办”；其他会话正常推进。此处选择暂停，是因为业务步骤通常依赖前一步结果。

调整方向的消息若在被接收前遇到停止或重启，仍保留在队列并显示“这条消息尚未处理，请重新发送。”，提供“重新发送”：复用原输入 ID 与引用恢复排队并继续队列，不创建重复消息。

消息发送失败时保留原文和附件，按同一客户端输入 ID 重试；不会以双份用户消息触发两次运行。输入草稿、待办和展开状态按会话隔离。

## 询问与确认

询问卡与确认卡出现在原轮相关工具的位置，并在输入区上方提供“有 1 项待处理”的定位入口。只显示同一个请求的不同入口，不复制多份可独立提交的卡片。

| 类型 | 需要显示 | 提交后 |
| --- | --- | --- |
| 补充信息 | 问题、必要上下文、选项或输入、必填状态 | 先显示正在提交；后端接收后显示用户答案并继续 |
| 操作确认 | 具体动作、目标对象、影响范围、允许的决定 | 按真实权限策略推进工具；拒绝原因可交给助手调整方案 |

未选择的默认选项不等于用户已回答。普通输入框中的补充不自动解决指定确认请求。两处同时提交或请求过期时，显示权威决定，禁止在错误轮次继续执行。

阻塞式询问使轮次等待；可并行推进的非阻塞问题不伪造整个会话暂停。只有后端策略实际要求授权时出现确认卡，不为读取、常规草稿编辑和所有工具调用统一加确认。

## 停止与恢复

“停止本轮”停止继续生成和工具派发，并请求取消本轮拥有、配置为随轮取消的前台调用与运行。后台运行及其他来源的运行不受影响；存在例外时在停止区说明仍会继续的对象。

发送与停止始终占用同一个 32px 圆按钮，使用主题中性色。点击停止后立即进入等待状态，禁止重复停止及键盘发送；输入草稿保留。停止请求 ACK 只表示收到意图。收到权威终态前显示“正在停止”；不可中断的外部操作显示“仍在收尾”。若最终仍成功完成，按真实结果显示，并说明停止未能阻止该操作。按钮不提供“撤销一切”的暗示。

| 情况 | 保留内容 | 恢复动作 |
| --- | --- | --- |
| 工具失败后助手仍可修复 | 原调用错误与后续 attempt | 本轮继续，不直接标整轮失败 |
| 本轮失败 | 已保存版本、已有正文、运行引用、错误边界 | “让助手处理”创建带失败引用的新轮 |
| 用户停止 | 停止前产生的内容与成果 | 新输入开始新轮；暂停的待办可显式继续 |
| 服务中断 | 已落盘内容；进行中对象标记需要核实或已中断 | 查询恢复能力，不自动重放未知外部操作 |
| 查看旧请求 | 原始内容与当时引用 | “基于此继续”形成新请求；不静默覆盖后续历史 |

“重试工具”“重新运行流程”“让助手处理”是不同操作。只有后端声明该调用可安全重试时提供工具重试；重新运行产生新的运行 ID，默认保留原输入和版本并在有版本变化时说明。撤销工作流编辑也不能撤回外部 HTTP 或 MCP 操作。

## 状态与事件契约

以下是设计契约，落地时以独立 Rust 后端为事实来源；不要求接入某个第三方编排框架。

| 对象 | 最小字段与语义 |
| --- | --- |
| Input | `id / projectId / clientInputId / sessionId / deliveryMode / targetTurnId? / contentParts / references / status / revision`；投递状态与执行状态分开 |
| Turn | `id / projectId / sessionId / initiatingInputId / status / phase / startedAt / endedAt / finalItemId? / revision` |
| Item | `id / turnId / ordinal / kind / status / revision / content / references / sealed`；用户补充同样拥有身份 |
| ToolInvocation | `callId / itemId / toolName / source / target / arguments / attempts / resultRef / status / cancellation / retryPolicy` |
| Interaction | `id / turnId / itemId? / kind / blocking / status / allowedResponses / expiresAt? / revision` |
| WorkflowChange | `id / turnId? / workflowId / beforeRevision / afterRevision / origin / diffRef` |
| RunReference | `runId / turnId? / callId? / origin / cancellationScope`；运行事实仍在运行域维护 |

Turn 生命周期为 `running → waiting_input / waiting_approval → running → completed / failed / interrupted`；停止时先进入 `stopping`，再由终态确认。模型排队、连接恢复、工具执行等属于 `phase` 或连接状态，不混为“失败”。

工具调用完成不完成 Turn；一次模型响应结束不完成 Turn；正常 Turn 完成也不自动完成关联 Run。会话列表按这些对象派生状态，避免另存一套与事实不一致的状态机。

事件至少携带 `eventId / projectId / sessionId / turnId? / itemId? / sequence / revision / kind / payload`。作用域由服务端建立；展示顺序使用稳定 ordinal，时间戳仅用于显示。快照返回 watermark，增量事件与历史按 ID、revision 合并；发现事件缺口时读取有界快照再继续。

建议读取面分为会话轮次摘要、按轮分页内容、单次工具详情、待办与待处理请求快照；SSE 发送这些对象的增量。前端可保存展开、滚动和选中引用，不能持有队列调度锁或轮次完成判定。大参数、输出和运行轨迹按需读取，不把全部正文塞进全局会话快照。

原型开发阶段不兼容旧消息模型。缺少 Turn / Item 身份的旧测试记录直接清理，不增加迁移、兼容展示或重复消息存储；现行模型的记录和模型连接配置保留。对话、历史与模型上下文统一从 Turn / Item 读取。

## 滚动与动效

常规工具调用直接执行，由结构化工具行显示进度，不要求模型逐次报幕。只有关键发现、阻塞、需要用户处理或最终结果才输出说明。过程文字仍属于原轮次，跨轮模型上下文仅携带用户输入、最终答复与执行事实，避免重复报幕成为后续回答的模板。

- 跟随底部时才跟随新内容；上翻阅读时出现“回到最新”，不抢焦点、不强制滚动。
- 加载旧内容、展开工具或收到终态补全时，保持当前条目和条目内偏移。完成收起保留用户展开意图。
- 流式文本只追加到稳定 Item，不重新创建整轮，不逐 chunk 重播动画，不对整段回复持续做平滑滚动。
- 工具开始到结束保持同一行，状态文字预留空间；展开使用短过渡，拖拽不做宽度补间；遵循减少动态效果。
- 屏幕阅读器只播报状态转换和需要处理的事项，不播报每个 token；所有展开、定位、回复与停止入口可键盘使用。

## 实施顺序与验收

### 第一批：正确组织一轮工作

Rust 增加 Turn、输入身份、有序 Item、工具完整生命周期及最终答复 phase；前端拆出轮次投影、过程组、工具行、成果引用和本轮状态。运行中、历史与刷新使用同一个读取模型。已有工作流与运行 API 保留独立边界。

验收：两轮各调用多个工具时不串轮；实时文本转终态不重复；工具开始即可见；失败工具不会显示成功；发起异步运行不提前报通过；刷新后顺序、内容与状态一致。

### 第二批：输入、停止与用户介入

实现服务端持久待办、幂等发送、明确的补充能力、真实询问与确认、停止确认和失败恢复。组件只发产品意图，由后端推进；流程内 Agent 与外部 MCP 接入同一引用与来源体系。

验收：发送超时重试不重复执行；队列消息可编辑移除；补充恰逢轮次结束不丢失或改投；停止未确认不提前报停止；请求过期或双重提交不执行两次；未知外部结果不自动重放。

### 第三批：长会话与跨版本回看

实现轮次摘要分页、过程按需加载、内容块级虚拟化、阅读锚点、精确版本比较和历史成果定位。再增加旧请求分支、跨轮检索等能力。

验收：长轮次与大量工具输出不会撑满全局状态；向上加载不跳动；回到旧成果能看见当时版本；其他会话、手动编辑和外部调用不污染本轮变更归属。

发布前用同一组样例覆盖：读取 → 编辑 → 校验 → 运行；运行中补充；待办；需要回答；需要确认；工具失败并恢复；整轮失败；取消中；连接中断；Turn 已结束而 Run 仍在运行。
